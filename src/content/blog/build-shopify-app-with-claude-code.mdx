Claude Code can help inspect a Shopify app repository, propose changes and work with current platform documentation. It does not remove the need to understand authentication, permissions, data boundaries and deployment. Start with one feature and review the generated changes before expanding the scope.

This is a documentation-based workflow, not a report of an app we built or installed. It replaces the earlier fixed completion-time promise and outdated scaffolding instructions. The commands below come from current Shopify documentation; the sample prompt is illustrative and has not been execution-tested.

## Choose the right development path

An externally hosted app is appropriate when the required functionality needs a maintained server, integration or developer-controlled interface. A theme change, Flow workflow or Sidekick-generated admin tool can be a smaller solution for other tasks. Use the [surface comparison](/blog/shopify-flow-sidekick-custom-app) before committing to an application you will operate.

For the developer path, confirm app-development permissions and an authorized dev store. Keep production credentials and customer records out of example prompts. A dev store supports testing without treating the live merchant store as a disposable fixture.

## Start from the current scaffold

Shopify's [scaffolding tutorial](https://shopify.dev/docs/apps/build/scaffold-app) currently recommends the React Router template for most embedded apps. Use the current Shopify CLI and follow its requirements, rather than copying older Remix-specific route assumptions into a new project.

Run the following in the parent directory where the project should be created:

~~~sh
shopify app init
~~~

Choose the React Router app option and the organization associated with the dev store. Review the generated files before asking for changes. Then enter the generated project directory and start the documented local development loop:

~~~sh
shopify app dev
~~~

Confirm the selected store and requested permissions during the preview installation. These commands create or connect resources in an authenticated Shopify context; use the intended development account. A running local preview is the starting point for verification, not a production release.

## Give Claude current Shopify context

The [Shopify AI Toolkit](https://shopify.dev/docs/apps/build/ai-toolkit) connects supported coding tools with Shopify documentation, schemas and validation capabilities. Its current recommended Claude Code plugin installation command is:

~~~sh
claude plugin install shopify-ai-toolkit@claude-plugins-official
~~~

Review the toolkit's current requirements and capabilities before enabling it. Documentation access and code validation do not guarantee that the app's business logic is correct. Authenticated store-management capabilities also need a clear boundary around what the assistant may execute.

## Ask for one reviewed change

Start with a feature that has explicit inputs and expected output. For example, a developer might add a read-only screen listing product titles and review links. This is a development exercise, not a substitute for the separate [Sidekick catalog-QA brief](/blog/one-prompt-shopify-admin-app).

> Inspect this generated Shopify app before editing. Propose one read-only product-list feature using the existing authentication and routing patterns. Use current Shopify documentation and validate the proposed GraphQL query. Do not request write scopes, add billing, change live records or deploy. Explain pagination, empty results and failed requests. Show the files you intend to change, then provide a reviewable diff and test plan. Report checks actually run separately from checks still required.

Review the proposal before accepting a broad refactor. If the assistant asks for unrelated permissions or rewrites working authentication, resolve that before continuing. Keep configuration changes visible in the diff alongside application code.

## Validate behavior in the dev store

Use known test products, including more records than fit on one page if pagination is part of the feature. Check empty results and controlled failures. Confirm the app does not expose one shop's data to another context and does not perform writes when it is meant to read.

Run the project's documented checks, inspect the UI and record failures as well as successes. The [AI app acceptance guide](/blog/test-ai-built-shopify-app) provides a merchant-facing evidence checklist. A screenshot of the first page cannot prove complete catalog coverage or correct authorization.

## Deploy the right components

Shopify's [app-version deployment documentation](https://shopify.dev/docs/apps/launch/deployment/deploy-app-versions) distinguishes app configuration and extensions from the web application. Releasing an app version does not host or release your web server. Plan hosting, secrets, persistent storage where needed, monitoring and a rollback route for the implementation you actually built.

Do not introduce a fixed hosting-price or completion-time promise without a measured configuration and current vendor terms. Use the [replacement cost worksheet](/blog/shopify-ai-app-replacement-cost) to account for implementation, review and ongoing maintenance. Ship when the defined feature passes its checks and someone owns its operation, rather than when a prompt finishes generating code.
